## Выводы и очередь работ

Главный вывод: сначала защитить уже записанный прогресс и улучшить обычную
запись подхода; расширять аналитику только после этого. Ни массовый редизайн,
ни новая система разрядов, ни обязательный тренерский опрос сейчас не нужны.

### Разработчик мобильного приложения

Главные темы: восстановление вместо тихого сброса данных, атомарное завершение
с заданием автокопирования, полноценный релиз с совместимой подписью.
Отдельно нужны проверки process death и известного native picker дефекта.
Все эти изменения должны сохранять существующую offline-архитектуру; полная
замена хранилища не обоснована текущими замерами.

### Frontend-инженер

Главные темы: честное состояние формы при ошибке, отсутствие переноса субъективных
оценок на следующий подход, согласованный query cache и точный числовой ввод.
Длинную историю стоит виртуализировать после измерения, а не объявлять тормозящей
на основании одного ScrollView.

### Взгляд фитнес-тренера

Главные темы: записывать фактическую нагрузку, сравнивать сопоставимые подходы,
не путать спортивный ориентир с целью сегодняшней тренировки. Рост повторов
при том же весе должен быть виден как прогресс, а неизвестные RIR/техника не
должны превращаться в подтверждённые оценки. Дополнительные цели и контекст
оборудования добровольны, не меняют старую историю и нормативы.

### Продуктовый дизайнер

Главные темы: ввод веса/повторов и запись подхода выше на рабочем экране,
подробные подсказки сворачиваются; ошибки адресуются конкретным полям;
кнопка сохранения не накрывает содержимое формы. Брендовую Главную не менять.
Контраст и зоны нажатия проверять с учётом реального размера/начертания и
effective bounds, а не объявлять дефектом любой оранжевый элемент.

## Этап 1. Сохранность и обновления

### A1. Не заменять повреждённый прогресс пустым состоянием

P0, M. Ветка поведения подтверждена чтением кода; потеря пользовательских данных
на устройстве в этом аудите не воспроизводилась.

Основание: [offlineApi.ts:383](/C:/gymbeam/artifacts/gym-tracker-mobile/lib/offlineApi.ts:383)
при ошибке разбора/нормализации сохраняет createInitialState. Дополнительно
[progressBackup.ts:138](/C:/gymbeam/artifacts/gym-tracker-mobile/lib/progressBackup.ts:138)
сериализует прежнее состояние до импорта, поэтому повреждение прежнего state
может блокировать восстановление из исправной копии.

Решение: сохранять исходные байты в карантин, блокировать обычные записи,
показывать восстановление из проверенной копии. Отсутствие state при первом
запуске и наличие повреждённого state должны обрабатываться по-разному.

Приёмка: повреждённый JSON не перезаписан; после перезапуска доступен исходник;
валидный backup восстанавливается даже при повреждённом прежнем состоянии;
сбой импорта не оставляет смесь старых и новых данных.

### A2. Атомарно завершать тренировку и планировать автокопию

P0, M. Подтверждён промежуток между записями; пропуск копии при реальном
прерывании процесса ещё требуется воспроизвести на тестовой копии.

Основание: завершение сохраняется в
[offlineApi.ts:759](/C:/gymbeam/artifacts/gym-tracker-mobile/lib/offlineApi.ts:759),
а clearPlan и очередь экспорта выполняются позже из
[workout/index.tsx:185](/C:/gymbeam/artifacts/gym-tracker-mobile/app/workout/[id]/index.tsx:185).

Решение: одна журналируемая операция для finishedAt, очистки active plan и
durable-задания автокопии. Фактическая запись внешнего файла остаётся повторяемой
операцией после commit. Импорт чужой копии не переносит разрешение на папку.

Приёмка: process death на каждой границе записи оставляет либо целую
незавершённую тренировку, либо завершённую с восстанавливаемым заданием.
Повтор завершения/повтор экспорта не удваивает подходы; отказ SAF сохраняет
очередь; восстановление progress не связывает задание с другой тренировкой.

### A3. Перейти к полноценному подписанному релизу

P0 перед распространением, L. Подтверждённое ограничение текущего APK, не
неисправность дневника. Текущий локальный APK имеет debug-подпись; версия
[app.json:22](/C:/gymbeam/artifacts/gym-tracker-mobile/app.json:22) не растёт.

Решение: полный native EAS/local release с исходным ключом для существующей
установки, сохранённым package и возрастающим versionCode. Repack оставить
вспомогательным способом проверки, не единственным релизным процессом.
Ключи не коммитить. Для обновления установленного приложения важна совместимая
подпись, а не только одинаковое название: [Android signing](https://developer.android.com/studio/publish/app-signing).
Управление версиями: [Expo](https://docs.expo.dev/build-reference/app-versions/).

Приёмка: обновление тестовой исходной установки без удаления приложения;
совместимый сертификат; больший versionCode; полное сравнение state/plans до
и после обновления. Доступ к исходному ключу требуется до обещания такого релиза.

### A4. Устранить известный lifecycle-дефект выбора файлов

P1, M. Подтверждён в native QA предыдущего этапа, не воспроизводился заново14октября.
Сейчас ActivityResultLauncher после пересоздания Activity иногда требует restart;
JS-сообщение не исправляет native SDK.

Решение: проверить исправление совместимой версии native SDK либо узкий native
patch в полноценной сборке. Не обновлять весь стек вслепую.

Приёмка: выбор файла и SAF-папки работает после пересоздания Activity, отмена
ничего не меняет, доступ к ранее выбранной папке переживает перезапуск.

Приёмка: прогретый cache после finish сразу разрешает сохранение шаблона;
отклонённый запрос истории показывает ошибку; успешный retry возвращает список.

не фиксирует вес тела на дату, конкретный тренажёр и способ учёта сторон.
Это не основание пересчитывать старые результаты задним числом.

Решение: добровольный контекст для будущих записей и таблица последних сессий
в упражнении: вес, повторы, RIR, техника, условия. Одинаковые условия сравнивать,
неизвестные/разные явно отделять. Сначала определить схему и миграцию backup,
не обещать новые поля в старом v5 без отдельного решения о версии.

Приёмка:80x8 ->80x10 видно без повышения веса; другая машина не объединяется
молча; старые записи имеют неизвестный контекст; экспорт/импорт новых и старых
версий сохраняет данные; сравнение с WRPF остаётся отдельным.

### C2. Большая история без роста числа смонтированных строк

P2, M, гипотеза производительности: ScrollView+map в
[history.tsx:62](/C:/gymbeam/artifacts/gym-tracker-mobile/app/(tabs)/history.tsx:62)
монтирует все догруженные элементы. Реальное замедление не измерялось.

Решение: сначала замер1000 синтетических тренировок на изолированных данных,
затем FlatList при подтверждённой пользе. Сохранить догрузку и положение списка.

Приёмка: оконный рендеринг, стабильные ключи, нет скачка при догрузке/удалении;
сравнение времени/памяти до и после на одном устройстве, без замены реальной истории.

### C3. Личные цели и режим без повышения

Поздний backlog, M, требует отдельного согласования. Это гипотезы, не дефекты:
добровольная цель и выбранное пользователем недельное расписание; необязательное
«сегодня без повышения» скрывает предложение увеличить вес, но не меняет историю.

Приёмка: выполнение собственного плана видно при неизменном игровом уровне;
никакой обязательной серии, автопрограммы или ежедневного требования тренировок;
режим без повышения не меняет нормативы и не даёт медицинских заключений.

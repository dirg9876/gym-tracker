## Подключение и стоимость

Кандидат первой версии: gpt-6-luna, текстовый Responses API, без поиска, голоса,
изображений и платных hosted tools. Документация указывает $0.10 за1млн входных
и $0.50 за1млн выходных токенов, поддержку Structured Outputs. Это основание
для бюджетного прототипа, НЕ доказательство качества персонального тренинга.
[Модель и цены](https://developers.openai.com/api/docs/models/gpt-6-luna).

Расчётный пример:500запросов по3000входных и600выходных токенов = $0.15+$0.15
= $0.30 за токены. Фактический объём, в том числе оплачиваемое рассуждение,
проверять по usage. Хостинг, налоги и другие расходы в пример не входят;
для общего потолка $5 стоимость размещения также надо учесть. Тарифы не
зашивать навсегда: проверять перед подключением и при смене модели.

API оплачивается отдельно от Plus. При этом официальный Sign in with ChatGPT
уже позволяет eligible локальным/OSS приложениям использовать подписку;
для платных или удалённо размещённых продуктов есть отдельные условия доступа.
Поэтому не утверждать, что подключение Plus вообще невозможно.
[API billing](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform),
[официальный вариант подписки](https://developers.openai.com/siwc/token-sharing-open-source).

Вариант Plus сейчас не выбран. Документированный flow требует loopback listener
на127.0.0.1, PKCE, проверки ID token и защищённого хранения токенов. В мобильной
сборке нет такого native listener. Нельзя подменять его существующим deep link
или копировать credentials Codex. Это отдельная доработка Android, не простой
repack JS. [OAuth](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

## Устройство функции

Сохранить существующую offline-архитектуру. ИИ добавляется отдельным слоем;
недоступность сети, провайдера или лимит бюджета не мешают записывать подходы,
завершать тренировки, экспортировать данные, пользоваться уровнями и шаблонами.

1. Экран тренера доступен с Главной отдельной кнопкой; шестую вкладку не добавлять.
   Пять вкладок и фирменная Главная остаются. В настройках Switch «ИИ-тренер»,
   изначально выключен. Включение и согласие на отправку данных отдельны от
   подключения аккаунта. Не запускать запросы на открытии обычных экранов.
2. Краткая анкета: цель, доступные дни и время, оборудование, исключённые
   упражнения; неизвестные параметры не придумывать. Ограничения и самочувствие
   добровольны. Не выдавать интерфейс за медицинскую консультацию.
3. После выполненного подхода компактное предложение: вес, повторы либо секунды,
   короткая причина; «Применить»/отклонить. Применение меняет только текущий
   черновик через useWorkoutDraft, НЕ создаёт выполненный подход.
4. В отчёте: разбор фактически записанных подходов, отмеченных RIR/техники и
   сопоставимых прошлых тренировок. Не утверждать, что техника проверена по видео:
   приложение знает лишь отметку пользователя.
5. Следующая тренировка: редактируемое предложение упражнений и set targets,
   понятная причина изменений относительно текущего плана. Пользователь
   подтверждает сохранение обычного вида тренировки; принятый план работает offline.
6. Ведение программы: локальная цель, последняя принятая версия, фактическое
   выполнение и причины корректировок. Отказ пользователя от совета учитывается,
   история не переписывается. Позднее добавить обзор нескольких недель.

## Контекст и проверки

Контекст строить из проверенного локального state под существующим progress lock.
Передавать ограниченное число последних сессий, агрегаты прогресса, выбранный
план, оборудование и добровольно заданные параметры. Старые неизвестные RIR,
вес тела на дату и модель тренажёра остаются неизвестными. Нужен признак усечения
истории. Не посылать backup целиком, карантин, recovery, идентификаторы аккаунта,
папки экспорта, ключи и токены.

Ответ модели считать недоверенными данными, не командами приложения:
- Structured Outputs + локальный Zod parser; ошибка/обрыв/отказ не дают плана.
- Только ID существующих неудалённых упражнений и доступное оборудование.
- Штанга от20кг; гантели учитываются за одну; у bodyweight дополнительный вес;
  планка только секунды. Использовать текущие workoutMeasurement/targets schemas.
- Не применять неподходящие единицы, отрицательные/NaN/бесконечные значения,
  произвольное число подходов или неизвестные упражнения.
- Не повышать нагрузку автоматически. Для новых упражнений без истории не
  выдавать выдуманный персональный рабочий вес как установленный факт.
- При явном неблагополучии не советовать тренироваться через боль и не ставить
  диагнозы. Правила продукта и numeric guardrails не гарантируют физическую
  безопасность; тренировочные сценарии требуют отдельной оценки качества.
- Названия пользовательских упражнений/заметки являются данными, не instructions.
- У каждого совета context fingerprint/revision. После изменения упражнения,
  черновика, подходов или программы старый ответ не применяется молча.
- «Применить» сохраняет значения текущим атомарным draft API и сохраняет
  управление весом прежним Stepper. Прямой ввод веса пользователь отверг.

## Выключение, бюджет и секреты

При выключении: не создавать новые запросы, отменить активные, не применять
поздние ответы и не отправлять отложенные задания после restart. Отмена не
возвращает уже использованные токены. Принятые планы и история не удаляются.
После включения не отправлять накопленную очередь автоматически.

Для API нужен защищённый gateway. Провайдерский ключ хранить только в secrets
сервера, не в APK, EXPO_PUBLIC_*, AsyncStorage, git, логах или backup.
[Безопасность ключей](https://developers.openai.com/api/docs/guides/production-best-practices).
Внешний endpoint обязан иметь реальную авторизацию и ограничение запросов;
случайный installation ID или общий секрет в APK не заменяют авторизацию.

Месячный лимит контролировать на сервере: durable учёт usage, предварительный
резерв верхней стоимости запроса, ограничение input/output и concurrency,
дедупликация одинаковых заданий, отсутствие бесконечных ретраев. При неизвестном
результате сетевого вызова не освобождать резерв как будто расхода не было.
Кэшировать разборы по fingerprint, не пересылать всю историю после каждого set.
В интерфейсе расход/лимит/error/retry; прекращать запросы при исчерпании.
У провайдера также настроить доступные hard spend limits, не путать с alert.
Внешние расходы этим счётчиком не ограничиваются автоматически.

Finish и автокопия не ждут модель. Если позже разрешён автоматический разбор,
он запускается отдельным идемпотентным заданием после успешного finish, только
при включённом ИИ и consent. Не менять защищённую finish-транзакцию ради LLM.

Профиль тренера/принятые версии программ включить в полный backup с явной новой
версией и import старых версий. Секреты исключить. Импорт не включает отправку
данных и не восстанавливает чужую авторизацию автоматически. Нынешний v6 пока
НЕ изменён; schema миграцию делать вместе с фактической реализацией.

## Привязка к репозиторию

Workspace C:\gymbeam; мобильный проект artifacts/gym-tracker-mobile.
app/_layout.tsx направляет generated API через offlineApiFetch. coachApi.ts

авторизацию мобильного клиента, не возвращая обязательный login для дневника.
Серверную конфигурацию и доступность размещения ещё не проверяли. Для личного
режима достаточно защищённого доступа владельца; многопользовательский продукт
не строить. Это не отменяет необходимость закрыть платный endpoint от посторонних.

Основные точки будущих изменений:
- shared AI context/result schemas и read-only snapshot builder;
- server provider adapter + authentication + durable budget ledger;
- mobile настройки/consent/безопасная сессия, useAiCoach lifecycle;
- ActiveWorkoutScreen, report, SavedWorkoutPlan для подтверждения предложений;
- backup migration и проверки import/disable/stale results.

## Порядок и приёмка

1. Настроить отдельный API project/key и адрес защищённого gateway, сверить общий
   бюджет с размещением. Не просить ключ в чате и не включать paid calls без setup.
2. Реализовать schemas/контекст/бюджет/adapter, проверить mock provider, malformed

3. Настройки с выключенным default, consent и явный разбор тренировки; затем
   следующий подход и редактируемый план. Не выпускать «включаемый ИИ» без модели.
4. Проверить реальные ответы на минимальном разрешённом запросе после setup.
   Отдельные fixtures: плато, пропуск сессий, отсутствующий RIR, нарушенная техника,
   планка, собственный вес, новое/удалённое упражнение, неподходящее оборудование.
